# Wallza Identity — Mautic SSO integration

This plugin connects one isolated Mautic tenant to the WallzaOS identity service through a short-lived authorization-code flow. It uses Mautic's native `sso_service` integration hook; it does not replace Mautic's firewall or add a public endpoint that accepts a Supabase user ID.

## Tenant safety model

- Install this plugin only in the Mautic stack assigned to the corresponding Wallza organization.
- Configure `WALLZA_MAUTIC_TENANT_ID` with the immutable Wallza organization UUID for that stack.
- The WallzaOS server must validate the Supabase access token server-side with `supabase.auth.getUser(token)`, then require active membership in `organization_members` or the authorized `agents` record before issuing a code.
- The requested tenant/client ID and callback URL are selectors, not proof of membership. The WallzaOS server must resolve both against its protected tenant registry and reject mismatches.
- Do not use one shared HMAC secret or one Mautic database for multiple organizations.

## Configuration

The per-tenant Oracle provisioner generates `WALLZA_SSO_HMAC_SECRET` with `openssl rand -hex 32` and stores it in the tenant's private env file (0600). Configure these values in that file:

| Variable | Purpose |
|---|---|
| `WALLZA_MAUTIC_TENANT_ID` | The immutable Wallza organization UUID assigned to this Mautic stack |
| `WALLZA_MAUTIC_BASE_URL` | Canonical public HTTPS base URL for this Mautic tenant, including any path prefix |
| `WALLZA_SSO_AUTHORIZE_URL` | Trusted WallzaOS HTTPS authorization endpoint |
| `WALLZA_SSO_TOKEN_URL` | Trusted WallzaOS HTTPS one-time-code exchange endpoint |
| `WALLZA_SSO_ISSUER` | Exact `iss` value the WallzaOS token service signs into assertions |
| `WALLZA_SSO_HMAC_SECRET` | Per-tenant 256-bit secret shared only by this Mautic instance and the WallzaOS server |

The plugin fails closed unless the tenant ID and Supabase subject are UUIDs, the secret is exactly 64 hexadecimal characters, and the authorization endpoint, token endpoint, canonical Mautic base URL and issuer use HTTPS with no embedded URL credentials or fragments. The base URL and issuer must not contain a query string. It will not start an SSO flow with empty or placeholder settings.

After deploying an image containing this plugin, run `mautic:plugins:reload`, clear/warm the Mautic cache, then enable/publish **Wallza** under Mautic's Integrations settings. Mautic's integration helper exposes only installed and published integrations to the SSO login page.

## Authorization-code protocol

### 1. Browser redirect

Mautic creates a cryptographically random 256-bit `state`, stores it in the user's server-side Mautic session, and redirects the browser to:

```http
GET {WALLZA_SSO_AUTHORIZE_URL}
  ?response_type=code
  &client_id={WALLZA_MAUTIC_TENANT_ID}
  &tenant_id={WALLZA_MAUTIC_TENANT_ID}
  &redirect_uri={registered Mautic callback URL}
  &state={random session state}
```

The callback path is generated by Mautic's router for `mautic_sso_login_check`; the configured base URL supplies the trusted HTTPS origin. The WallzaOS server must compare `client_id`, `tenant_id` and `redirect_uri` against its protected tenant registry. Do not reflect an arbitrary callback URL.

The WallzaOS browser/session layer must establish the user's Supabase identity. Its server must validate the access token with Supabase Auth and authorize active membership in the requested organization (or the allowed agent membership) before issuing anything.

### 2. One-time code

After authorization, WallzaOS redirects to the registered Mautic callback with `code` and the unchanged `state`:

```text
{redirect_uri}?code={single-use-code}&state={original-state}
```

The code must be:
- cryptographically random and stored hashed server-side;
- single-use and consumed atomically at exchange time;
- short-lived (maximum 60 seconds);
- bound to the authenticated Supabase user, organization UUID, client ID, exact callback URI and state;
- rejected after membership is revoked, the account is disabled, or the user switches organizations.

Do not put Supabase access or refresh tokens in the redirect URL.

### 3. Server-to-server exchange

Mautic consumes the session state before making the outbound request, then sends:

```http
POST {WALLZA_SSO_TOKEN_URL}
Authorization: Basic base64({tenant-uuid}:{per-tenant-hmac-secret})
Content-Type: application/json
Accept: application/json

{
  "grant_type": "authorization_code",
  "code": "single-use-code",
  "client_id": "tenant-uuid",
  "redirect_uri": "exact-registered-callback",
  "state": "original-state"
}
```

WallzaOS must authenticate the tenant server, atomically consume the code, and re-check that the user still has active membership before issuing an assertion. Redirects are disabled on the Mautic HTTP client. The exchange must be HTTPS only.

Successful response:

```json
{
  "assertion": "header.payload.signature"
}
```

### 4. Signed assertion

The assertion is a compact JWT signed with HS256 using that tenant's 64-character hexadecimal secret. The protected header must be `{"alg":"HS256","typ":"JWT"}`. Required claims:

| Claim | Requirement |
|---|---|
| `iss` | Exact configured `WALLZA_SSO_ISSUER` |
| `aud` | Exact Mautic tenant UUID |
| `tenant_id` | Same exact tenant UUID |
| `sub` | Stable Supabase Auth user UUID/string |
| `email` | Valid email address |
| `email_verified` | Boolean `true` |
| `first_name`, `last_name` | Non-empty user names |
| `iat`, `exp` | Integer timestamps; issued-at may be at most 15 seconds in the future or 120 seconds old; lifetime cannot exceed 120 seconds |
| `jti` | Unique assertion identifier |
| `state` | The original Mautic session state |

Mautic verifies the signature with `hash_equals`, header algorithm/type, issuer, audience, tenant, state, verified email and time window. It rejects malformed, expired, unverified or cross-tenant assertions.

## Local Mautic user and role policy

The assertion is not a user-provisioning or role-assignment API.

1. WallzaOS must provision the Mautic user through the protected, tenant-local Mautic API before the first SSO login. Set the local Mautic `username` to the immutable Supabase Auth user UUID (`sub`); do not use email as the stable key. This provisioning path uses the tenant's server-side Mautic API credential.
2. Mautic looks up the local user by the exact Supabase UUID in `username`, requires the assertion's verified email to match the local Mautic email, and requires the Mautic account to be published/enabled.
3. If the local account is absent or disabled, authentication fails closed.
4. The plugin does not create users, enable accounts, or assign roles from JWT claims. The role remains the one assigned by the tenant's Mautic administrator.

## Tests and remaining dependency

The plugin's PHPUnit tests cover valid assertion verification, invalid signature, wrong audience/tenant, wrong state, expired/overlong assertions, non-UUID subject, unverified email, unsupported algorithms, session-state redirect, missing/disabled local users, stable subject mapping and local-email mismatch.

The Mautic-side implementation and contract are in this repository. The matching WallzaOS authorization-code and token endpoints are a separate backend change and are not yet implemented by this Mautic PR. Do not enable public SSO until both sides pass an end-to-end test with an actual Supabase session and a provisioned Mautic user.
